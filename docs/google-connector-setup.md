# Google connector setup for the app owner

Recruiters use **Connect Google**, choose an existing Form, map questions, and select an approved job. They do not create scripts, triggers, or webhooks. The following is one-time platform setup by the RecruitOS deployer.

1. Create or choose a Google Cloud project. Enable Google Forms API, Google Drive API, Cloud Pub/Sub API, and Cloud Scheduler API. Enable billing for Pub/Sub and Scheduler. Their free allowances are usage limits, not a guarantee of zero charges.
2. Configure the OAuth consent screen. For a test deployment, add the recruiter's Google account as a test user. Request `drive.readonly`, `forms.body.readonly`, and `forms.responses.readonly`. Broad Drive read access is sensitive; public production use may require Google verification. In an external OAuth app with publishing status **Testing**, refresh tokens for these scopes expire after seven days, so the recruiter must reconnect until the app is published and verified as applicable. Create an OAuth **Web application** client. Authorize `http://localhost:3000/api/google/callback` for local testing and the exact production URL for deployment. Put client ID, secret and redirect URI in server environment variables.
3. Create one Pub/Sub topic, such as `projects/PROJECT_ID/topics/recruitos-forms`, and a **pull** subscription, such as `projects/PROJECT_ID/subscriptions/recruitos-forms-pull`. Grant `forms-notifications@system.gserviceaccount.com` **Pub/Sub Publisher** on the topic. The topic must belong to the same Google Cloud project as the OAuth client.
4. Create a service account with **Pub/Sub Subscriber** on the subscription. Download a JSON credential, base64-encode the complete JSON without line breaks, and put it in `GOOGLE_PUBSUB_SERVICE_ACCOUNT_JSON_BASE64` on the server. Keep the original JSON private. Set `GOOGLE_PUBSUB_TOPIC` and `GOOGLE_PUBSUB_SUBSCRIPTION` to the fully qualified names above.
5. Set `APP_ORIGIN`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, a random 32-byte hex `GOOGLE_TOKEN_ENCRYPTION_KEY`, and a long random `CRON_SECRET`. The token key must be backed up securely; changing it requires reconnecting Google. Do not put these in browser-exposed variables.
6. Schedule `GET /api/google/sync` at a suitable interval with `Authorization: Bearer <CRON_SECRET>`. One Cloud Scheduler HTTP job every 5 minutes is a candidate. Configure its header only in the platform owner's project. The app also offers manual **Sync now**. This scheduler is required for automatic Pub/Sub pull, watch renewal, and missed-notification reconciliation.
7. Create or choose an existing editable Google Form with name and one PDF or DOCX file-upload question. Email is recommended but optional; missing email creates a Needs details application for recruiter correction. A consent question is not required. The Forms API cannot create file-upload questions. File upload requires the applicant to sign in to Google. Keep response files private.
8. Sign in to RecruitOS, create an approved job, click Connect Google, consent, choose the Form, map question IDs through the UI, and start monitoring. Submit a synthetic CV. Inspect the watch ID and expiry, Pub/Sub notification, synchronized response, private CV storage, processing attempt, and dashboard evidence. Test token refresh and watch renewal after a short-lived token expires and near watch expiry. Record actual outcomes in the evaluation package.

Forms watches expire after seven days and notify through Pub/Sub without response details. The sync worker reads responses and Drive file bytes through OAuth, deduplicates on Form and response ID, and reconciles even if a notification is delayed or missed. Unprocessable responses are recorded in `google_sync_failures` for retry and manual attention. A real watch was created and a synthetic response and private CV were fetched through official APIs on 2026-10-22. Actual Pub/Sub notification delivery and watch renewal are still unverified. Vercel Hobby runs the configured cron once daily; use Google Cloud Scheduler for a five-minute interval if faster monitoring is required.

The subscriber service account needs `pubsub.subscriptions.consume` through the Pub/Sub Subscriber role. That role does not include configuration read permission. The configured service account successfully called pull on the subscription with HTTP 200 and no queued messages. Pagination state is stored per Form so a large response backlog can continue on the next scheduler run. At most one pending application is analyzed per scheduled call.

## Reviewer-approved Gmail sending

Enable Gmail API in the same Google Cloud project. Add `https://www.googleapis.com/auth/gmail.send` to Google Auth Platform Data Access and keep the recruiter's Google account in Test users while the app is in Testing. The existing OAuth web-client redirect URI is reused. The reviewer clicks **Connect Gmail to send** on an application page; RecruitOS requests `openid`, `email`, and the send-only Gmail scope, then stores a separate encrypted refresh token and displays the verified sending account. Public use of this sensitive scope may require Google OAuth verification. Testing-mode non-basic refresh tokens can expire after seven days, so reconnection is visible in the UI.

To verify, use a synthetic applicant address controlled by the operator. Save a draft, inspect the saved recipient and full text, check the approval box, and click **Approve and send email**. Confirm the Gmail message ID in the board and the message in the recipient mailbox. Repeat only with synthetic mailboxes. If status is Delivery uncertain, inspect the sender's Gmail Sent folder before any new attempt. No Gmail inbox scope is requested; the app cannot inspect Sent mail itself. Local unit tests and build do not verify a live Gmail delivery.
